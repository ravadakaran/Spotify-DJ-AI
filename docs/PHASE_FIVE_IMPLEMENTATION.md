# Phase 5 implementation — 27 October 2026

TASK-020–023 software covers server-bounded interactions, hybrid fitting, durable session summaries and personal/admin UI. Normal-use held-out recommendation acceptance remains open. The Phase 0 licensed audio/model gates and independent sentiment evaluation remain open.

## Interactions

`interaction.record` is available through the existing socket command entry point and PUT `/lounges/:id/playbacks/:playbackId/interaction`. Its strict body is `{listenedThroughSeconds,liked?}`; omitted liked preserves the previous explicit preference; the socket includes playbackId. Membership and a connected room socket are required. Identity is server-owned; only the current playback can receive evidence. The browser sends ten-second heartbeats only when its audio element is playing and ready. Explicit likes send zero listen credit.

The reducer accrues per-identity current-playback availability while present and server playback is advancing. A heartbeat credits the minimum of client evidence, new available playback seconds, elapsed server time since that identity's previous heartbeat, and 15 seconds. Uncredited time beyond a heartbeat cap is discarded; explicit zero-second likes preserve the prior listen boundary. Total credit is capped by duration; completion is >=80%. Pauses, end-of-track and recovery downtime add no availability. Multiple tabs share one identity meter. Command receipts prevent duplicate effects within the existing bounded retry window. This measures bounded reported participation, not proof that a human heard audio. The final sub-ten-second browser tail may be uncredited; historical playbacks cannot be backfilled. Recovery resets interval meters and hydrates the previous durable credit/like on the next heartbeat; unflushed tail credit can be lost.

The writer upserts a unique `(loungeId,userId,playbackId)` projection in the same transaction as its event and checkpoint. Shared lounge/playback records infer co-attendance without user-pair arrays. `observedAt` records the latest signal time, preventing a late like from entering an earlier training cutoff merely because the row was created earlier.

## Recommendations

An administrator explicitly starts a worker-thread fit; only one fit runs at once. Bounds: 500 ready profiles, 50,000 interactions, 30 seconds. Above-capacity fits fail explicitly. Completion or like yields a binary user-item signal. Item-item collaborative cosine uses shared participants; acoustic similarity averages normalized BPM, circular Camelot number, energy and valence distances. Personalized scores blend 60% content and 40% collaborative; consumed positives are excluded. Cold users receive catalog popularity, with stable ID ordering for ties. Recommendation ranking does not authorize an immediate segue: existing BPM/Camelot hard checks still apply at every queue transition.

An artifact records algorithm/version, cutoff, SHA-256 data hash and fit count. It is saved before swapping the active reference; failure preserves the prior model. The last completed artifact loads on startup. Admin job reads exclude the private artifact. Requests return modelVersion, fallbackReason and cutoff asOf. Explicit admin refits implement refresh without deployment; periodic refits are not enabled. Interrupted running jobs may need a fresh fit after restart.

Run `node scripts/evaluate-recommendations.js dataset.json report.json`. Input contains tracks, interactions and cutoff; optional provenance/label declare origin. Training uses observations on/before cutoff and test uses later observations. Precision@5 divides by five per eligible user, excludes previously positive tracks, and reports content/collaborative/hybrid baselines, coverage, population, exclusions, counts and hashes. Users need five unseen candidates and at least one unseen held-out positive. Do not split one evolving observation across train/test; use separately captured sessions/observations.

The committed authored synthetic fixture has 28 metadata profiles and 12 identities, with 24 train and 60 test signals. It is a pipeline fixture, not independent preference evidence or normal-use interaction collection. Its exact measured metrics are in `evidence/phase-five-recommendations.json`. The Phase 5 acceptance gate still requires a declared normal-use/manual held-out dataset; synthetic success alone does not close TASK-020/021 acceptance.

## End barrier and analytics

Host-only `room.end` / POST `/lounges/:id/end` uses expectedRevision and the shared FIFO. It drains earlier events, accepts one end event, then drains that event together with the summary/checkpoint transaction. It returns 200 with revision acknowledgement and `summaryStatus:complete`, a documented synchronous completion of the originally planned asynchronous 202 contract. The public checkpoint retains pending as a hint; GET analytics is authoritative for summary completion. Failed persistence can leave the memory state ended/pending until writer recovery; it cannot expose a falsely complete durable summary. End cancels the active battle/proposal and pauses playback. Further application mutations and AI publication are rejected; subscriptions can still read the room.

The summary derives from all persisted canonical room events, across epochs: duration is first playback.start to room.end wall time (including pauses), zero if never started; peak is maximum distinct presence-set identities (including pre-playback attendance and the configured departure grace); battle count counts opens, questions count accepted requests including insufficient answers, sentiment preserves tick payloads, and track history preserves starts. Repeated command receipts do not add counts. Membership permits own-session analytics, including past/removed members; global admin has no implicit session access. Summary aggregation currently reads the full room event history in the end transaction; very long sessions need paged projections before production-scale rollout.

Dashboard returns only the caller's latest 50 durable interactions, taste weighted over latest 1000 records, and up to 50 active memberships. The response declares these limits and an asOf read time; it does not include the buffered tail. `/users/me/lounges` now pages by own membership createdAt/ID with limit 1–100 and an identity-scoped membership-ID cursor. Overview refreshes memberships when entering/leaving the console. The UI provides a recommendation rail, taste/history, quick rejoin, explicit like toggle, session-end control, expandable analytics with sentiment meters/track history and admin fit/status controls. Existing catalog upload/profile forms remain available.

## Migration and rollback

Migration `005-personal` adds interactions (unique composite index plus strict numeric/boolean validation), session_summaries, recommendation_jobs and an own-history membership index. No existing data is removed. It is idempotent under the checksummed migration runner. Existing snapshots default meter fields. Old binaries cannot replay interaction.record/room.end events. Before local rollout, stop the application and use the existing private Extended JSON backup/restore procedure in ENVIRONMENT_SETUP; preserve assets and the migration ledger together. Rehearse restoration to a separate database, review validators/indexes and use a compatible binary or full matching pre-rollout backup for rollback. Do not delete individual ledger entries or reset the private library. This implementation has not migrated the user's local database or deployed anything.
