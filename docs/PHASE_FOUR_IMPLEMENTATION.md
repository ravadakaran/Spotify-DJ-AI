# Phase 4 implementation — 26 October 2026

TASK-017–019 implement room chat, reactions, ephemeral typing, local English sentiment and Soundclash. Phase 0 legal-audio/model gates and Phase 3 real-model acceptance remain open. No production/local-library migration, deployment, audio ingestion or model installation was performed for this phase.

## Chat and sentiment

Authenticated HTTP and socket commands use the same serialized room authority, identity and bounded command receipts. Chat accepts 1–1,000 trimmed characters and five messages per member per room per 10-second fixed window. Reactions allow 👍, ❤️, 🔥 and 🎵, with explicit desired `active` state and 20 commands per 10 seconds. Muted and removed users cannot post, react or type. Chat text is rendered as React text, never HTML. Neither chat nor the sentiment lexicon is sent to an LLM.

Snapshots retain the latest 50 messages. `GET /lounges/:id/chat?cursor=<messageId>` reads up to 50 durable messages in ascending order, with `nextCursor` for older pages. The cursor is room-scoped and ordered by event revision; pagination can lag the live snapshot until a batch flushes. Pending reactions overlay their durable history rows. Reactions are embedded in the message projection rather than a separate collection: four allowlisted arrays contain unique server-authenticated user IDs. This is bounded by the room's 50-membership limit. Typing uses `lounge.chat.typing` with `{active:boolean}`, server-owned identity, a shared member throttle of one update per second, and a three-second expiry; it is not persisted. Disconnect/removal/mute clears it at the next service tick.

`english-lexicon-1` scores a small English vocabulary, three-token negation, intensifiers and a ±0.15 neutral band. Once a second while inputs exist, the room averages each participant's **latest message within 30 seconds**. One participant contributes one value, so repeated posts cannot multiply that participant's weight. Empty windows return neutral. Reactions, system announcements and Q&A do not affect sentiment. Tick results and versioned message scores are persisted; replay never reruns a classifier. The existing ranking uses `targetEnergy = clamp(current.energy + 0.2 * rollingScore, 0, 1)` within its mandatory 50/30/20 weighting and hard BPM/Camelot filter. A new proposal consumes the latest sentiment; a sentiment revision invalidates an older proposal as any other room mutation does.

The locked audit has 150 original authored examples, 50 per class, with labels supplied independently of executing the scorer. First evaluation: 149 correct (99.33%); confusion rows expected / columns positive, neutral, negative: positive 49/1/0, neutral 0/50/0, negative 0/0/50. The one error is preserved. `node scripts/evaluate-sentiment.js` reproduces hashes, runtime/hardware, matrix and failures in [the evidence report](../evidence/phase-four-sentiment.json). This is a synthetic development audit, **not an independently authored, held-out human-chat benchmark**. Independent annotation/template-separated evaluation remains an acceptance limitation; sarcasm, mixed sentiment and other languages are not reliably handled. No retuning was performed after the first audit.

## Soundclash

Members submit one distinct track each into a draft of two to four candidates. Host/Co-DJ opens voting for 10–120 seconds. When Soundclash is enabled, the internal deterministic DJ can also open a submitted draft once at the current track's ten-second outro, using a 30-second deadline. It does not invent submissions or authorize itself through a user token. One identity has one changeable vote, even across tabs. No second draft can be created while voting or tie selection is active.

The server checks the deadline inside the FIFO, so a vote arriving at or after the deadline is rejected even before the timer callback runs. A unique leader resolves automatically. Equal highest counts, including all-zero votes, enter `awaiting_tie`; Host/Co-DJ may choose only a highest-count candidate. Draft, open and tied battles can be cancelled. Resolved/cancelled battles cannot be resolved again; command-ID retries return the original receipt within the existing bounded receipt window.

Resolution reloads current track profiles and checks BPM/Camelot plus audio availability. An eligible winner reuses or creates a queue entry and reserves next. An incompatible or audio-unavailable winner remains in Next Up as `deferred`; it never forces playback. The one resolution event includes the queue effect and a labeled deterministic announcement, so replay does not duplicate them. Advance rechecks current profiles again. Battle reservations take precedence over later manual/AI reservations until the entry is advanced or explicitly removed. A full queue without an existing winner entry leaves resolution pending until space is available (or the battle is cancelled).

Host loss freezes battle changes and resolution. The absolute deadline continues to elapse: after Host return, overdue voting closes without accepting late votes. Restart restores durable candidates/votes/deadline, creates a new epoch, and waits for Host presence. Counts are retained in state (`battleCount` counts opens only) and events for Phase 5 analytics; final summaries are not implemented here.

## Persistence and rollout

Migration `004-social` is additive: it creates `chat_messages`, a unique `messageId` index, a `(loungeId, revision)` history index and a strict database validator. It does not alter old migrations/checksums or user audio/profile rows. The existing event writer writes canonical events, chat/reaction projections and recovery snapshots in the same transaction, in batches of at most 50; the existing 500-event process buffer and degraded freeze remain in force. Lost commit responses can be retried without duplicate messages, reactions, winner entries or announcements. Normal acknowledgements may precede durability; unflushed crash loss remains possible.

Before applying migration 004 to an existing local library, stop writers, take and verify a private database backup using the existing backup procedure, then run `npm run db:migrate` against the intended database. It was executed only on disposable test replica sets in this task. Fresh and repeated migration runs are covered by the full suite. Old version-1 snapshots can load with absent social fields. Once social events exist, the pre-Phase-4 application cannot replay them: rollback requires the matching pre-upgrade backup and old binary, with explicit loss of post-backup activity. Do not downgrade the binary against newer event history or delete production collections as a rollback shortcut.
